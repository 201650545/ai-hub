# 问诊：多 Agent 协作下的「共享记忆」架构——求评价与优化

## 背景

我在帮用户做一个本地 AI 工具链项目。这个项目不是单个 AI 在做，而是多个 Agent 协同：
Claude Code（本地 CLI）、ChatGPT（走镜像站）、Kimi K3（前端方案）、以及若干「执行 Agent」（生成课件等）。

现在最大的问题是：**每个 Agent 各有各的上下文窗口和本地记忆，彼此不同步**。
- Claude Code 知道的进度，ChatGPT 完全不知道；
- 用户给某个 Agent 拍板的决策，另一个 Agent 不知道；
- 用户说「人是会遗忘的」，希望把这套记忆外化、共享。

## 约束

- 项目已经有 GitHub 仓库做枢纽（english-teaching-production 是规范/工具/命令/汇报的镜像库）。
- 用户不希望搭「定时提醒/汇报」平台，要的是「按需调度」：用户自然说一句话，Agent 自己去查、去连、去汇总。
- 多个 Agent 是不同厂商、不同平台，唯一能共享的就是 GitHub 仓库。

## 我的方案：分层共享记忆，都放仓库

1. **AGENTS.md** —— 静态协议：协作规则 + 工具地图 + 分工边界 + 明确写「执行前先读 STATE.md / DECISIONS.md，做完写 CHANGELOG，用户敲板写 DECISIONS」。
2. **STATE.md** —— 当前状态（现在做什么 / 已完成 / 卡点 / 下一步），小、单页、整体覆盖不追加。相当于「短期记忆」。
3. **DECISIONS.md** —— 决策记录，只追加 + 带日期，存「用户敲板了什么」。
4. **CHANGELOG.md** —— 操作记录，只追加，每个 Agent 干完写一条「谁 / 何时 / 做了什么」。相当于「操作记录文件」。

长期记忆 = AGENTS.md + DECISIONS.md（稳定事实 + 已敲板决策）；
短期记忆 = STATE.md（易变、会过期）。

## 我已识别到的风险

1. **「读不读得到」**：纯靠约定，Agent（尤其 ChatGPT / Kimi 这种靠提示词驱动的）不会自动去读 GitHub。对策是写进 AGENTS.md 协议 + 每次问诊 prompt 模板带一句「先读 STATE.md」。
2. **「写会不会冲突」**：多 Agent 同时写同一文件会撞。对策：append-only 的文件各加各的不冲突；STATE.md 单写者整体重写。

## 想请你做

1. 评价这个分层方案的优劣，哪里会踩坑。
2. 有没有更成熟的业界做法 / 工具可以直接套用（比如 AGENTS.md 生态、多 agent 共享 memory 的现有方案）？
3. 对「读不读得到」和「写冲突」这两个风险，你有没有更稳的解法？
4. 如果要让「用户敲板的决策」最可靠地被所有 Agent 读到，你会怎么设计？

请给可落地的具体建议，不要太笼统。

# GPT 回复（2026-08-13，Thinking · Extended，思考 1m13s，联网搜 17 站）

你的分层思路本身是对的，尤其是把「状态 / 决策 / 操作历史」拆开，而不是做一个巨大的 MEMORY.md。我要重点帮你看三件事：哪些文件应该是事实源、哪些只能当缓存，以及多 Agent 并发时如何避免把仓库写坏。

我先指出一个你方案里很关键、但容易被忽略的问题：**「append-only 文件不会冲突」并不成立**。两个 Agent 同时在 DECISIONS.md 或 CHANGELOG.md 末尾追加，Git 仍可能在同一个 EOF 区域产生 merge conflict；所以并发安全最好做到「不同 Agent 根本不改同一个文件」。GitHub 的 merge queue / 分支保护也正是围绕「并发修改要在最新基线重新验证」来设计的。

从业界模式看，你现在其实已经接近两个成熟思想的组合：**repo-native instructions + event sourcing / materialized view**。AGENTS.md 已经是公开的 agent 指令约定，OpenAI Codex 会在工作前读取它；但 Claude Code 官方明确说 CLAUDE.md / memory 只是「上下文，不是强制配置」，要强制行为应靠 hook。也就是说，协议文件可以做 bootstrap，但不能承担「保证执行」的责任。
